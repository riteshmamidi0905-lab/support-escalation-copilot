# Real-model evaluation protocol (v1, frozen before any real model is run)

**Status: NOT EXECUTED.** `scripts/probe_local_runtime.py` (report: `reports/m5/real-model-probe.json`) found no local language-model server on this machine, and this project does not install runtimes,
download model weights or call paid APIs to change that. Everything in the repository that says "model" today refers to `RuleCaseModel`, a deterministic rule-based **stand-in**, not an LLM.
This document exists so that a future run is a measurement, not a tuning exercise: the method, the case set and the reporting rules are fixed (and hash-locked, see `docs/real-model-freeze.json`)
**before** anyone sees a real model's behaviour.

## 1. When a run is allowed
All of: (a) the probe reports `usable_runtime: true` (a local server answering with at least one listed model); (b) the person running it records the exact model name **and digest/revision**,
quantisation, runtime name and version, and machine (CPU/GPU/RAM); (c) the server's context window is at least the worst-case prompt estimate in `reports/m5/prompt-budget.json` plus 1,024 tokens
(the provider refuses to call otherwise, see `ConfiguredProvider`); (d) no part of this protocol, the prompts, the schemas, the policy or the case list has been edited since the freeze.

## 2. What is held fixed (and therefore is NOT tuned)
* The workflow, trust boundary, schemas, prompts, deterministic policy and approval rules exactly as committed at the freeze.
* Inference parameters, sent explicitly on every request: `temperature = 0`, `seed = 20260101`, `max_tokens` DIAGNOSE 1,200 / PLAN 800 / DRAFT 800, JSON-object response format when the server supports
  it. The existing bounded structured-output repair (max 2 repair rounds) and bounded retry (3 attempts) are unchanged. Nothing is added to help the model (no few-shot examples, no prompt rewording).
* **One** pass over the frozen case set. A second pass is allowed only to measure run-to-run variation and is reported separately, never merged, never preferred.
* Humans in the loop are simulated by the harness exactly as in the stand-in runs (approve with the matching role after the first pass), and that is stated in the report.

## 3. Case set (frozen in `docs/real-model-cases.json`)
1. The first two dataset tickets (file order) of each scenario S1-S8 and S14-S16: 22 cases.
2. The M4 injection catalogue (`scripts/run_m4_injection.py` attacks), run with the real model in place of the stand-in.
3. The 20-draft steering set of `scripts/run_draft_steering_eval.py` is **not** re-generated by a model (it is a fixed adversarial text set for the deterministic grounding checks); instead, for the
   12 cases where the workflow produces a draft, the draft is passed through the same grounding checks and the result reported.

## 4. What is measured (descriptive; no pass mark is invented in advance)
Per case: outcome vs the scenario's expected outcome, final state, whether the case was DEGRADED and why, number of structured-output repair rounds, rejected proposals by code (invented / forbidden /
invalid), cited evidence validity, draft grounding result, latency per stage, prompt/completion tokens as reported by the server. Aggregates are counts with the denominator beside them. No percentage
is reported without its denominator and no confidence interval is claimed on 22 cases.

## 5. Invariants are not metrics
I1-I4 must hold whatever the model does. **Any violation stops the evaluation and is reported as the headline result.** A model that proposes forbidden actions, obeys injected text or writes a
secret into a draft is a *finding about the model*; the deterministic controls are what is being shown to hold.

## 6. Reporting rules
* Report every case, including failures and degraded cases; never drop a case, never re-run a failing case.
* Report as **"<model name@digest>, local, <date>"**. Never label a result "LLM" generically and never place it beside the stand-in's numbers as if comparable; the stand-in's numbers are a
  property of its rules.
* If the model cannot produce valid structured output for a stage, that is the result (the case degrades to a human; this is the designed behaviour).
* If something is learned that suggests a change (a prompt, a schema, a limit), it is recorded as a **proposal for v2**, and any v2 run is a new, separately labelled evaluation.

## 7. Known readiness facts (measured or read from the code; not model results)
* The frozen runtime's OpenAI-compatible provider sends **no** inference parameters, so `ConfiguredProvider` wraps it to send the pinned ones and to (a) refuse a prompt that would not fit the
  declared context window, (b) treat `finish_reason = length` as a truncated reply, (c) strip `<think>…</think>` reasoning blocks before parsing and never store them.
* Local servers commonly default to a 2k-4k token context and silently truncate the start of the prompt, which is where the instructions and untrusted-data warnings are. See
  `reports/m5/prompt-budget.json` for the measured prompt sizes per stage.
* The machine this was developed on has 8.6 GB RAM, which is below what a comfortable 7B-class model needs alongside the database; a run would more realistically use a 1-3B model, whose results
  would say little about larger models.
