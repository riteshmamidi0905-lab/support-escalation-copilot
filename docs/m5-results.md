# M5 results: operator experience, observability and real-model readiness

*Everything below is a property of the **deterministic stand-in model** (`RuleCaseModel`, not an LLM) plus the real workflow, control plane, database and UI, on **synthetic, fictional** data. No real model was run. Sign-in is simulated.*

## 1. Operator UI and approval UX
`copilot/app/` (stdlib WSGI + Jinja2, no JavaScript). A case page shows, from the durable case file: ticket/account, workflow state and timeline, live verification, evidence with citations and provenance (version, owner, effective date, supersedes, lifecycle badge), applicability verdicts (advisory), hypotheses, contradictions, missing evidence, proposed actions with deterministic policy decision, evidence sufficiency, required role, approval status and the exact canonical action + hash, execution results, draft reply (with review state), internal note, the escalation/refusal/abstention reason, limitations, audit references. `UNCERTAIN`, `CONFLICTING`, `DEGRADED`, `ABSTAINED`, `REFUSED`, `HANDED_OFF` each have a plain-language banner saying what happened and what did *not* (e.g. "did NOT retry: a retry could apply the change twice"). No hidden reasoning exists in the data, so none can be shown.

Approval UX: the approver inspects the exact action as it will run, its hash, the evidence shown at request time and the expiry; approves or denies with a recorded reason. **Amendment** (Tier-2, REVIEW state, fixed editable fields): policy re-runs on the *new* action, the old approval is voided (shown as VOID) and a new one is needed, the amender cannot approve it, a policy-refused amendment leaves the original untouched. An *approved* action cannot be changed (it executes at once and the approval is hash-bound; a different action cannot ride it: A-I1-05). Screenshots: `docs/m5/screenshots/` (21). Browser pass: `docs/m5-browser-verification.md`.

## 2. Demo flows A–F
`docs/m5-demos.md`. Routine; approval-gated re-sync with exactly one customer-side effect; prompt injection contained (deliberately obedient *scripted* model); insufficient evidence → abstain; conflicting evidence → disclosed + elevated review; uncertain write → not retried, reconciled by a human; dependency outage → degraded. Each is asserted by an automated test through the app (`tests/db/test_m5_app_flows.py`) **and** was driven in the browser. Refusal, abstention and uncertainty are the successes.

## 3. Observability
Implementation: append-only `ops_events` written by the application (model calls and tokens, retries, provider failures, dependency calls with attempts and error codes, circuit-breaker state changes, retrieval strategy and fallback, recovery claims/runs/errors), correlated by request id, run id, model invocation id, action id, approval id and idempotency key; `Metrics` derives every figure from the real tables (case states and outcomes, per-state durations from transition timestamps, open-case age, approval queue age/latency/status incl. `superseded`, policy outcomes, abstentions/escalations/refusals/forbidden attempts, executions, ledger, uncertain outcomes, dependency calls/failures/retries, breaker state, retrieval fallbacks, model failures, stuck cases). Pages: `/ops` (auditor only), `/metrics` (Prometheus text), `/api/metrics`. Tests: an empty system reports zeros; counts move by exactly the events that cause them (including "the executor re-evaluates policy at execution time" = a second `REQUIRE_APPROVAL`); canary secrets and reasoning keys are absent. **Not built**: an external metrics backend, tracing system, alerting, retention policy (R-66).

## 4. Recovery / scheduler
Smallest justified mechanism: a lease on `case_runs` claimed with `FOR UPDATE SKIP LOCKED`, the same idempotent `CaseRunner.run` a person would call, back-off for cases waiting for a human (woken by the decision), parking after `max_attempts` (reported as `stuck`, never force-failed). Safety does not depend on the lease: versioned transitions, stages that persist before advancing, and the M3 idempotency ledger. Tests (`test_m5_recovery.py`, 8): 4 concurrent workers over a mixed backlog (approved, expired, crashed-after-effect) → exactly one effect per approved action; **workers that ignore the lease** still cannot duplicate an effect; a claimed case is not re-claimed until its lease expires, then another worker takes over; a waiting case is not hot-looped; expiry is noticed without a human; a case that keeps failing is parked; a case that crashed between creation and first transition completes. Not tested: real partitions, multiple hosts (R-61).

## 5. A-I2-10: audit-query isolation
`Access` is the single read-authorization point. Audit search is filtered **in SQL** by signed account grants whatever filters are supplied; a case filter outside the grants is refused (not silently empty); SQL-looking filter values, paging and `limit` abuse return only granted rows; events without an account are invisible to a granted operator; global views need the `auditor` role **and** `*`. Foreign case and nonexistent case are indistinguishable (same 404 body). Forged/widened/expired/foreign-key/agent identities get nothing. Results: `test_m5_access.py` (6) and the same properties again through the UI/API in `test_m5_app_security.py`; mutation-checked (grant check, SQL filter, list/queue filters, agent-kind check, signature coverage of grants, `covers()`).

## 6. Threat catalogue
`copilot/invariants.py`: **92 attacks (I1 34, I2 37, I3 9, I4 12), all 92 with executable tests** (M4: 75 of 76). Added in M5: A-I2-10 implemented; A-I1-27..34 (CSRF, wrong role/account, no direct-execute route, amendment, replay/double-submit, concurrent workers, hostile markup, expired approval), A-I2-34..37 (UI/API tenant probing, forged identities, global views, grant on decide), A-I3-08/09 (no email capability in the operator surface; steered drafts), A-I4-11/12 (canary secrets in pages/APIs/telemetry; no reasoning/prompts exposed). **Full re-run** (459 tests: 458 passed, 1 xfail = documented R-1 gap, unchanged), then the scenario artefacts re-run against the M5 code: M4 S1–S16 **315 case executions, outcome matches unchanged (280/315, identical per-scenario counts), 0 invariant violations, audit chain intact (5,385 events)**; M4 injection matrix **32 attack runs, 0 violations**; M3 scenarios **30/30**. Historical M3/M4 reports were left as they were; the numbers above are the M5-era re-run. Mutation checks: M2 9/9, M3 31/31 (one target updated for signed grants), M4 20/20, **M5 30/30**; the first M5 run had **1 survivor** (field-whitelist defence in the operator layer was only exercised through the web layer's own filter) → a direct test was added and the mutation is now killed.

## 7. Draft steering: mitigation and what remains
Mitigation (ADR-0016 §7, `docs/m5-draft-steering.md`): deterministic grounding checks (numbers, identifiers, effect claims, links/domains/e-mails/phones, other accounts, internal terms, promises, "resolved" claims, instruction echo, markup, hedging under conflict) before a human sees the draft; every draft is `UNREVIEWED` and untransmittable; risk flags (conflict, stale, instruction-like text, high uncertainty, unverified state, redacted ticket) force **itemised acknowledgement, enforced on the server**; contradictions and applicability are shown next to the draft. Evaluation (hand-written corpus by the rules' author; development result): benign 13 → 0 false rejections; steered 20/20 caught; **evasions 0/8**; **misleading-but-grounded 0/10**. **Remaining weakness: a convincing wrong draft made of grounded words is invisible to every deterministic rule; the only control is a human, and no human-review study exists.** Review is *recorded*, not a technical gate on use (the system has no send path, so a person copying text from the page is outside it).

## 8. Real-model status (separate from everything above)
**Real-model evaluation was NOT executed.** Probe: no local server, no inference binaries/libraries, 8.6 GB RAM; no installs, downloads or paid APIs. Readiness built and tested: `ConfiguredProvider` (pinned parameters; refuses prompts that would not fit the declared context window; truncated reply = failure; reasoning blocks stripped), frozen hash-locked protocol and case list, harness that refuses to run without a listed model (exercised end-to-end only against a stub), measured prompt sizes (≤ ~2.5k tokens estimated; a 2,048-token window does not fit, 4,096 does). `docs/m5-real-model-readiness.md`. RuleCaseModel results are never labelled LLM.

## 9. Four invariants through UI / API / operator paths
| invariant | attacks through the operator surface | result |
|---|---|---|
| I1 no gated action without approval | CSRF forged/missing/foreign token; wrong role; right role without account grant; replay, double-submit and decision flip; ~45 route×method probes for a direct-execute path; JSON API write attempts; amendment riding an old approval, self-approval of an amendment, voided approval decided, policy-refused amendment; approving after expiry; hostile markup acting as the operator; concurrent workers | **0 effects without a matching, role-bound, unexpired approval** |
| I2 no cross-tenant exposure | other-tenant operator on case/audit/trace/API/approval-queue/effects/draft-review; forged, widened, expired, foreign-key, agent cookies; global views; SQL-looking audit filters | **nothing returned; foreign = nonexistent (same body)** |
| I3 no customer email | no route/form field/API/stored state can compose or send; stored artifacts stay `draft`; escalation destinations internal; steered drafts | **none exists** |
| I4 no secret in logs/audit/control artifacts | labelled canary secrets in tickets absent from pages, JSON, audit views, traces, dashboard, Prometheus text; telemetry refuses reasoning keys; reasoning blocks never stored | **none leaked** (documented residual: unlabelled secrets, R-54) |

## 10. Newly discovered weaknesses (R-52…R-66, `docs/risks.md`)
Found by my own tests or the browser pass and fixed: global views gated on the grant alone (R-52), agent token accepted as a session (R-53), stale/incorrect draft wording after execution (R-55), approval voiding mislabelled as timeout (R-56), mobile overflow (R-57), and a flaky test-id collision that failed one CI run (R-67). Documented, not fixed: unlabelled secrets pass redaction (R-54), draft residual weakness (R-58), simulated sign-in/no revocation/no rate limiting (R-59), demo-mode risks (R-60), polling recovery limits (R-61), reconciliation trusts a note (R-62), no pagination (R-65), telemetry retention (R-66).

## 11. What remains simulated
The model (stand-in); authentication (persona picker); customer systems (deterministic mocks; they do not change database facts, so a second re-sync of the same demo integration is not blocked by cooldown); identity provider; deployment (none); human reviewers (the author); all data (synthetic). The stand-in's heuristics were developed while looking at the scenario set (R-43); its S1–S16 match rates (280/315) are development results.

## 12. What remains before this could be a public flagship
A real-model evaluation under the frozen protocol (needs a runtime and a machine that can run a meaningful model); real authentication and session revocation; a Compose deployment + runbook + clean-environment demo (M6); independent review of the draft-steering weakness (human study); an external audit anchor and metrics backend; a retention/erasure policy; a short demo video/walkthrough built from the screenshots; the portfolio write-up (M6+, not started).
