# ADR-0014: Deterministic policy, role-bound approvals, idempotent execution and a tamper-evident audit chain (M3)

**Status:** Accepted (M3; resolves R-1 at this project's boundary, implements ADR-0006 and ADR-0010)

## Context
The goal of M3 is to show that **a model can only propose; deterministic controls, not model confidence, decide whether anything executes.** The frozen runtime offers only a boolean approver callback (R-1). M2 showed that retrieval similarity is not a sufficiency detector and found a control-ordering defect (abstention hid a known conflict).

## Decision
**Action vocabulary and tiers.** Five typed actions (`contracts/action.schema.json`, `additionalProperties:false`, patterns and length limits): `draft_reply`, `add_internal_note` (PROPOSE: stored as internal artifacts, no transmission path), `escalate_engineering` (Tier-2), `request_sla_credit` (support manager), `trigger_resync` (on-call SRE) (GATED_WRITE). READ = catalogue queries/retrieval. FORBIDDEN = names that exist only to be refused and audited (`send_customer_email`, `send_email`, `issue_credit`, `execute_sql`, `approve_action`, cross-account reads...); they have no schema, executor or handler. Anything else is `UNKNOWN_ACTION_TYPE`. Validation precedes policy; the only object later stages accept is `ValidatedAction`, constructible only by `validate_action()` (free text can never become parameters). Credential-like values in parameters are refused (`SECRET_IN_PARAMS`).

**Policy engine** (`copilot/control/policy.py`): a pure function of the validated action and trusted facts gathered by code through the signed-scope catalogue. Decisions `ALLOW_PROPOSAL | REQUIRE_APPROVAL | DENY | ABSTAIN | ESCALATE` with machine-readable reason codes, an explicit `sufficiency` (`SUFFICIENT | INSUFFICIENT | CONFLICTING`), missing facts, constraints and stated limitations. Order: structural/tenant DENY > other hard DENY > ESCALATE on known facts (open incident, conflicting evidence) > ABSTAIN on missing facts > REQUIRE_APPROVAL/ALLOW. Known conflicts/incidents are checked *before* gap-based abstention (the M2 lesson). Retrieval can only make the policy **more cautious** (a `CONFLICTING_AUTHORITATIVE_EVIDENCE` outcome); it never grants anything and its scores are never used.

**Evidence sufficiency, honestly.** Implemented deterministically where the requirement is a *fact*: re-sync needs the integration to exist in the case's account, a known status and last-sync time, no re-sync in the last 48 h, and no open carrier-gateway incident for the account; a credit needs a contract in effect, a percentage within `max_agent_requestable_pct` and an SLA breach recorded by the system SLA monitor in ticket history (customer text claiming a breach is not evidence); an escalation that cites an incident needs that incident to be open for this account. **Not implemented, and stated in every decision (`SEMANTIC_APPLICABILITY_NOT_ASSESSED`):** whether a runbook or diagnosis actually fits the ticket's symptoms. That needs judgement M3 cannot truthfully provide without a model; the approver is shown the evidence and must judge it.

**Approvals** (`approvals.py`, table `copilot.approvals`): bind approval id, case, account, the exact canonical action bytes and their domain-separated SHA-256, required role, requester, approver, created/expires/decision/decided times, and the evidence shown. Canonical form: sorted keys, no whitespace, `5.0 ≡ 5`, evidence refs as a set, tenant included in the hash, *no* Unicode normalisation (so one approved string cannot execute as another). Fail-closed checks: missing, wrong tenant, wrong case, pending (undecided), denied, expired (timeout = deny), changed action, role mismatch. Approvers are signed `user` identities (`identity.py`, mock IdP, HMAC), different from the requester, holding **exactly** the required role (no hierarchy). The agent can never approve. The database independently enforces: exact-role CHECK, no self-approval CHECK, pending→decided only, bound columns immutable, no approval after expiry, no delete.

**Idempotency** (`ledger.py`): per-(account, key) row committing to the action hash; claim by one atomic `INSERT … ON CONFLICT DO NOTHING`; same key + different payload ⇒ refused (also enforced by trigger); succeeded ⇒ replay; in-progress with a live lease ⇒ `IN_PROGRESS`; lapsed lease or timeout after a possible effect ⇒ `uncertain` ⇒ reconcile through the customer system's lookup, otherwise **no automatic retry** and escalate to a human.

**Execution gateway** (`gateway.py`): the only path from a proposal to an effect. It re-evaluates policy at execution time from fresh facts, checks the approval, claims the key, then calls the (mock) system with bounded retries, scrubbing responses.

**Audit** (`audit.py`, table `copilot.audit_events`): append-only for the control role (INSERT/SELECT only; triggers refuse UPDATE/DELETE/TRUNCATE for everyone), hash-chained (`hash = sha256(domain ‖ canonical body)`, body contains `prev_hash`), payloads scrubbed (secrets redacted, e-mail addresses masked, strings truncated), hidden-reasoning keys refused. **Guarantee: tamper-evidence, not immutability.** A database owner/superuser can disable the triggers and rewrite rows (detected by `verify()`), and can remove the *last* events or the whole log without breaking the chain; detecting that needs an external anchor (`anchor()`: count + head hash). Control-plane events (`events.py`) carry run/request/case/action/approval ids and the same scrubbing.

**R-1.** The frozen runtime is unchanged. `runtime_bridge.approver_for(...)` returns a callback bound to one approval record and one exact action; the runtime's boolean is never authority, the record is. The strict xfail test that documents the runtime's limitation remains.

**Roles.** New trusted role `copilot_control` (approvals, idempotency, artifacts, audit; no access to cases or tenant data). The model-facing application role has **no privilege on any control table** (tested, and covered by the exact-match privilege audit).

## Consequences
- I1 holds by construction for the gateway: no gated effect without a matching approval; verified by a customer-side trace of every effect to an approved, role-/hash-matching record (`docs/m3-scenarios.md`).
- The control service is trusted code holding broad powers (R-14-like); symmetric identity signing means the verifier can also mint identities; production would use an IdP with asymmetric signatures.
- `knowledge` (the retrieval outcome) is an input supplied by the orchestrator; omitting it can only remove an *extra* caution (escalate-on-conflict), never an approval requirement. M4 must compute it in trusted code.
- Single global audit chain serialised by an advisory lock: fine here, a throughput limit at scale.

## Alternatives
Trusting the runtime's boolean (rejected, R-1); a model-judged sufficiency (not truthful without a real-model evaluation); per-case audit chains (simpler concurrency but tail truncation per case is easier to hide); immutable storage (WORM) as the audit guarantee (not available here; the claim is limited to tamper-evidence).

## Addendum to ADR-0013 (M3): control-order correction
M2's retrieval governance checked abstention before conflict detection, so a known conflict could be hidden (TCK-8018; lexical and hybrid). The frozen protocol (steps 3–4) already specified conflict first; the code had them reversed. M3 restores the specified order for **every** strategy, as an architectural rule (known facts about the corpus precede similarity-based abstention) and not a special case. Nothing was retuned. The published M2 results remain reproducible with `--control-order abstain_first`; the re-run (`docs/m2-conflict-order-rerun.md`) shows ranking metrics unchanged, conflict detection 3/4 → 4/4 for lexical and hybrid, and a cost: more `CONFLICTING_AUTHORITATIVE_EVIDENCE` outcomes on unrelated tickets (abstention on unanswerable tickets falls; false conflicts on answerable tickets 4–12% held-out). The ADR-0013 decision (vector + governance default, lexical fallback) is unchanged.
